# PostgreSQL 15 服务器 schema v2：显式升级与回退

本页只适用于 `docker-compose.server.yaml` 的 PostgreSQL 15 服务器路线。便携版 PostgreSQL 17 由 Launcher 管理，不能调用这里的迁移命令。这里的操作步骤不表示正式实例已升级；发布和实际执行前，应先用同版本镜像及生产备份的**隔离副本**演练。

## 不变的安全边界

- 先停止所有连接目标库的 Web/worker 写入，并核对连接已排空。迁移器会再次检查当前数据库的客户端连接，使用事务、互斥锁和旧表排他锁；它不会替操作员停止进程。
- 先完成目标库的 PG15 自定义格式备份（`pg_dump -Fc`），记录 SHA-256，并在新的隔离 PG15 目标实际恢复、核对业务行。迁移入口会核对摘要、`PGDMP` 格式、PG15 TOC、库名和旧表清单；TOC 核验本身不等于恢复演练。
- 仅接受冻结的 PG15 无版本旧结构或完整 v2 结构。未知表/索引/结构、其他业务 schema、错误版本、其他数据库连接及已存在的目标应用角色都会拒绝；不会在普通 Web 启动时自动升级或修补。
- 管理员连接仅用于显式升级。v2 Web 使用新建的低权限角色，不拥有建表、迁移审计或超级用户权限。`DB_ADMIN_*` 不得进入挂载到 app 容器的 `.env`；操作员应从独立受保护的 Compose 环境文件或进程环境提供它们。
- 升级后不能直接用旧应用镜像运行 v2，更不能让 v1 程序读取 v2。先冻结/验证与当前源码对应的镜像标签；不要依赖可变的 `latest`。本仓库不自动切换正式 Compose project、卷、`.env` 或真实数据库。

## 隔离演练顺序

1. 核对目标库确为 PG15、当前结构与本仓库预期一致。为升级前数据库制作 `pg_dump -Fc`，计算 SHA-256，并在**新库**用 `pg_restore` 恢复后核对用户、任务及关键行数；不要向原库执行恢复。
2. 停止目标库的全部应用写入。使用管理员 DSN 和待创建的新应用角色口令作为**进程环境变量** `QB_SERVER_ADMIN_DATABASE_URL`、`QB_SERVER_APP_PASSWORD`，不要写入命令行、Git、日志或 app 容器环境。管理员 DSN 必须指向要迁移的目标业务库。
3. 从仓库根目录运行：

   ```text
   python -m scripts.upstream.migrate_server --database-name <目标库名> --app-role <新应用角色> --backup <PG15 自定义格式备份绝对路径> --backup-sha256 <64 位小写 SHA-256> --pg-restore <pg_restore 绝对路径> --confirm-stopped "我已停止所有连接此数据库的业务进程"
   ```

   退出码 0 的 `applied` 表示本次提交成功；`already_applied` 表示完整 v2 指纹、审计和权限重新核对通过。任何失败都保持停写，保留原备份并排查，不要换一个未知库反复尝试。
4. 为新 Web 镜像设置 `DB_USER` / `DB_PASSWORD` 为新应用角色及口令；旧管理员账号保留为 `DB_ADMIN_USER` / `DB_ADMIN_PASSWORD`，只供 postgres 服务环境使用。显式设置 `QB_SERVER_APP_DATABASE_URL` 为新应用角色的完整 URL，保证旧 `.env` 的 `DATABASE_URL` 不会覆盖它。URL 中的特殊口令字符须正确 URL 编码。不要把管理员密码留在 app 挂载的 `.env`；迁移前逐项检查配置来源。
5. 固定 `QB_SERVER_IMAGE` 为已验证的 v2 镜像标签，并设置 `QB_SERVER_PULL_POLICY=never`（使用本地已核验镜像时），再启动 app。旧环境未设置这些变量时，Compose 仍使用原有镜像、拉取策略和同一数据库账号默认值。PG15 旧卷不会因 `POSTGRES_USER/PASSWORD` 环境变量变化而自动改角色或重置口令。
6. 验证应用以受限角色启动、能按两个独立用户读取各自数据、无 DDL/迁移审计访问，然后才恢复正常流量。`state/` 的通知去重和本地文件仍应保留现有挂载；PG dump 不替代这些文件的备份。

## 回退与数据窗口

数据库结构不做原地降级。若 v2 启动失败，保持停写，使用旧制品和迁移前备份在**新的隔离 PG15 库/卷**恢复并核验。若 v2 已有新写入，先统计迁移后写入窗口并让数据所有者决定是否接受丢失；不能静默覆盖原库、删除新表或把 v2 卷交给 v1 镜像。不要对正式 `postgres_data` 或正式 `.env` 做自动清理。

## 本仓库的合成验收

固定隔离容器 `qb-b2-pg15-fixture-20260929-1`（独立同名卷，仅 `127.0.0.1:59538`）验证了：旧库备份/隔离恢复，显式迁移和重复调用，未知结构与错误备份拒绝，建表后注入故障的事务回滚，并发调用，受限角色与双用户读取。合成 Compose 配置分别核对了旧默认和 v2 管理员/应用角色分离；Linux 测试容器只读挂载当前源码，不挂载真实 `.env` 或 `state/`。这些证据不表示正式服务器数据库或最终发行镜像已升级。
